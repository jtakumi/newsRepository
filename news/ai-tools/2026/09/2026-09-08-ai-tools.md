### 1. LiteLLM / v1.101.0-rc.1（Cohere Parse OCR・Auto Router のUI設定・過負荷時 503 自衛・MCP 既定認証）

- 種別: OSS / LLM ゲートウェイ（RC / pre-release）
- 関連: OpenAI 互換 API / Cohere / Azure AI / Anthropic / Grok / MCP
- 公開・更新日: 2026-09-06 03:20 UTC（JST 2026-09-06 12:20）※ `v1.101.0-rc.1`（pre-release）
- 概要: 多数のLLMプロバイダを OpenAI 互換 API で束ねる LiteLLM の、安定版 `v1.100.0`（09-07 記事で採用）に続く次期 `.101` ラインの最初の RC。約 60 件超の追加・修正が含まれる。主な新規点は、**Cohere Parse（OCR）を Cohere / Azure AI 経由で対応**、**Grok-4.6 の Azure AI 向けコストマッピング追加**、**Admin UI から Auto Router をワンクリック設定**、**per-worker admission control（各ワーカーが過負荷分を 503 で拒否）**、**MCP の `x-mcp-<access_group>-*` ヘッダを既定の upstream 認証情報として送出**、**カスタムガードレールの非ブロッキング `flag()` 判定**、**Redis バッチ読み取りの同期最適化**、**Prometheus メトリクスの別プロセス化（フラグ）**、**cosign による Docker イメージ署名検証**など。
- 何が便利か:
  - **ドキュメントOCRをゲートウェイ経由で**: Cohere Parse により、OCR をアプリ側で個別実装せず LiteLLM 経由で扱える。
  - **モデル振り分けの設定が容易**: Auto Router を Admin UI からワンクリックで設定でき、ルーティング調整の手間が減る。
  - **過負荷時に自衛できる**: per-worker admission control で、あふれた分を 503 で返すため、ゲートウェイ全体の巻き込み障害を防ぎやすい。
  - **MCP 認証の既定化**: アクセスグループ単位の認証情報を既定 upstream に使え、社内 MCP 連携の設定が簡潔になる。
- 使いどころ: 複数プロバイダを集約する社内 AI ゲートウェイ、OCR を含むドキュメント処理パイプライン、負荷制御が要る本番手前の検証環境。
- 開発者にとっての価値: `pip install "litellm==1.101.0rc1"` で `.101` 系機能を先行検証できる。過負荷制御・OCR・MCP 認証の運用機能は個人の自作ゲートウェイでも流用しやすい。
- 注意点: **RC（pre-release）** のため本番投入は要検証。安定版は `v1.100.0`。大規模更新のため、既存のコールバック・予算・ルーティング設定は段階的に検証すること。
- 公式リンク: https://github.com/BerriAI/litellm/releases/tag/v1.101.0-rc.1
- 参考リンク: https://github.com/BerriAI/litellm/releases
- メモ: 09-07 記事は安定版 `v1.100.0` を採用し、`v1.101.0-rc.1` は「RC のため見送り」としていた。本記事では RC を新規採用（実質的な新機能が窓内で確認できたため）。

#### 使用例

```bash
# RC を先行検証（PyPI のプレリリース版）
pip install "litellm==1.101.0rc1"

# OpenAI 互換ゲートウェイとして起動（config で複数プロバイダを集約）
litellm --config config.yaml
```

### 2. GitHub Copilot CLI / HydraFusion（research preview・マルチモデルオーケストレーション）

- 種別: CLI 機能 / マルチモデルオーケストレーション（research preview）
- 関連: GitHub Copilot / OpenAI / Anthropic ほか（複数プロバイダのモデルを併用）
- 公開・更新日: 2026-09-01 公式発表（GitHub community discussion #206492）。app / VS Code 連携は 9 月中に展開予定で、直近も開発者コミュニティで話題継続。
- 概要: Copilot CLI 上で、タスクごとに最適な実行ワークフローを自動選択し、複数プロバイダのモデルを組み合わせる実験機能。ワークフローは 3 種類。
  - **Single**: 選ばれた 1 モデルが直接タスクを解く。
  - **Cascade**: 軽量モデルが下書きし、品質ゲートが基準を満たすか判定。満たさなければより強力なモデルへエスカレーション。
  - **Critique**: 別系統のモデルが下書きを批評し、原著者モデルが 1 回だけ修正する。
- 何が便利か:
  - **単一の最強モデル固定より安く、品質を保てる**: GitHub のオフライン評価では、TerminalBench 2.1 で Claude Opus 5 比、検証済みタスク品質 +4.9pt・推定ワークフローコスト −67%。
  - **プロバイダ横断で最適化**: 1 つのワークフロー内で複数プロバイダのモデルを使い分けられる。
- 使いどころ: コスト意識の高い日常のコーディング、長時間タスク、CLI 中心のワークフロー。
- 開発者にとっての価値: **全 Copilot プランで利用可**。Copilot CLI の `/experimental` から有効化でき、**HydraFusion 自体の追加料金はなし**（構成する各モデルを標準レートで従量課金）。
- 注意点: **research preview**。現時点は Copilot CLI のみで、app / VS Code 連携は 9 月中の展開予定。ベンチマークは GitHub 自社のオフライン評価であり、実タスクでの再現は要確認。
- 公式リンク: https://github.com/orgs/community/discussions/206492
- 参考リンク: https://www.marktechpost.com/2026/09/05/github-introduces-project-hydrafusion-runtime-multi-model-orchestration-that-builds-a-workflow-per-coding-task-in-copilot-cli/
- メモ: NewsRepository の既存 ai-tools 記事に HydraFusion の記載なし。直近で話題化が継続し、9 月中に対応クライアントが広がる見込みのため補完採用。

#### 使用例

```bash
# Copilot CLI 内で実行
/update            # 最新へ更新
/experimental on   # 実験機能を有効化
/model             # 一覧から HydraFusion を選択
```

```bash

/update
/experimental on
```
